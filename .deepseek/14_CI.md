## §14.1 Job layout

| Job | Runs on | Purpose |
| --- | --- | --- |
| `colcon` | `ubuntu-latest` + `ros:lyrical-ros-base` container | acados, codegen, build, gtest suite, **and the A7 parity test** (A1, A2–A5, A7, A8) |
| `python` | `ubuntu-latest` + `actions/setup-python` | pytest and the two reproduction notebooks (A6, A9) |
| `docs` | `ubuntu-latest` + TeX Live | compile the three derivations |

**The runner is `ubuntu-latest`, not `ubuntu-26.04`, deliberately.** The container supplies Ubuntu
26.04 regardless of the host image, and an `ubuntu-26.04` runner label may not exist (risk V1).
Do not "fix" this by pinning the runner unless you have confirmed the label. Keep the comment at
the top of the workflow saying so.

`ROS_DISTRO: lyrical` is a workflow-level env var so the distro name appears once rather than in
five places.

Target: the whole workflow under ~15 minutes. Beyond that people stop reading it.

## §14.2 acados and codegen — the slow steps

acados is built from source with a pinned tag ([§2.2](02_ENVIRONMENT.md)). This is the slowest
step and the most likely to break on a newer toolchain (risk V9).

**Cache it**, keyed on the acados tag *and* the container digest. Building it from scratch every
run is the difference between a 4-minute and a 14-minute job.

**Do not key a cache on the OS alone.** A stale cache of a source build is how you end up testing
last month's solver against this week's formulation, and the symptom is a parity failure that
looks like a bug in the controller.

Codegen (`generate_mpc_cbf_solver.py --all`, `generate_tube_solver.py --all`) runs **before**
`colcon build`, always ([02_ENVIRONMENT.md §2.4](02_ENVIRONMENT.md)). Cache it keyed on the acados
tag plus a hash of `codegen/` — and remember the `file(GLOB)` caveat in
[03_BUILD_SYSTEM.md §3.3](03_BUILD_SYSTEM.md): a restored cache that adds files after CMake has
configured will not be compiled.

## §14.3 rosdep

There is no rosdep key for acados. Whatever `--skip-keys` the workflow needs, list them
explicitly rather than swallowing failures with `|| true`: that idiom hides a genuinely missing
dependency and turns it into a missing-header error three steps later.

If you must use it, echo the rosdep output first so the log still shows what failed.

## §14.4 Tests

`colcon test --return-code-on-test-failure` followed by `colcon test-result --verbose`. Both are
needed: the first fails the job, the second prints *what* failed. Dropping the second produces a
red job with no diagnosis, which trains everyone to re-run rather than read.

Upload test results with `if: always()` so a failing run still yields its XML.

**Do not gate the timing assertion (A2) tightly in CI.** Shared runners give timings that vary by
several multiples. Assert a generous ceiling here to catch a catastrophic regression, and take the
real p95 from a local Release run with the CPU named ([10_TESTS.md §10.1](10_TESTS.md)). A
CI-derived solve time in the README would be a number you cannot defend.

## §14.5 A7 and A9 — the two criteria CI actually owns

**A7 (parity).** `cpp_solve_cli` exists only in the `colcon` job's build tree
([11_PYTHON_REFERENCE.md §11.5](11_PYTHON_REFERENCE.md)). Run the parity test **in that job**,
after `colcon test`, with a Python environment that has `acados_template` — which it does, because
codegen already needed it.

Running it in the `python` job instead means it skips, silently, and A7 is then **not verified by
CI** while the badge suggests otherwise. If you cannot wire it up, say so in the README rather
than letting the badge imply it.

**A9 (reproduction).** Execute both reproduction notebooks with
`jupyter nbconvert --to notebook --execute`. Because the notebooks assert their own numbers
([12_ANALYSIS.md](12_ANALYSIS.md)), a numerical regression fails the build. That is the entire
point of the job — **do not add `--allow-errors`**, and do not convert a failing assertion into a
warning.

The three analysis notebooks are slower and need no paper numbers to hold; run them on a schedule
or on demand rather than per push, and say which in the workflow comment.

## §14.6 The docs job

Compile all three derivations with `-halt-on-error`, three passes plus bibtex.
`if-no-files-found: error` on the artifact upload, so a silently empty build fails.

A broken derivation fails the job. That is intentional: the derivations are a deliverable
([13_DOCS.md](13_DOCS.md)), not decoration.

## §14.7 What is deliberately absent

- **No hardware or Gazebo smoke test.** There is no vehicle here. The nearest equivalent — a
  headless run of `2d_obstacle.launch.py` asserting `min h ≥ 0` — is worth adding once §9 is
  stable and would upgrade A8-adjacent confidence considerably. Until then, that check is manual.
- **No coverage gate.** Coverage on a library this size measures how many lines the randomised
  feasibility campaign happened to touch, which is not a quality signal. The parity check and the
  reproductions are the real coverage argument.
- **No auto-format commit.** Linting fails the build; it does not rewrite your code.
- **No commit of `c_generated_code/`.** It is a build artefact ([§2.2](02_ENVIRONMENT.md)).
  Regenerating it in CI is what proves the generators still work.
